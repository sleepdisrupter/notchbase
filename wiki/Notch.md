# The notch

`src/notch` is the heart of the app: a single `Notch` value per display that owns the shape's state machine, all of its springs, and the layers painted inside it. The app ticks it with the time and cursor, pushes events into it (a song started, the volume changed, a device connected, a tool posted a notice, a prompt arrived), and calls `Notch::ui` to paint it. `ui` returns the [actions](Architecture.md#data-flow) the user triggered.

| File | Role |
| --- | --- |
| `mod.rs` | the `Notch` struct, its public API (`tick`, `ui`, `show_*`, `set_*`, `open_page`, `collapse`, …) |
| `geometry.rs`, `moves/transition.rs` | geometry, silhouettes, morph springs and the motion table |
| `moves/` | how the shape moves: attraction and lean (`attract.rs`), docking (`hug.rs`), making room for menus (`dodge.rs`), running from the pointer (`flee.rs`, `flow.rs`), the strain before a peek opens (`surge.rs`) and the swell at start (`launch.rs`) |
| `pointer.rs`, `zones.rs` | the hover state machine and the hit zones |
| `activity/` | activities: starting and expiring them, lanes, messages, and the volume, brightness and device indicators (`volume.rs`, `device.rs`) |
| `notice/` | tool notices: `mod.rs` (`ToolNotice`, sizing, measuring and painting), `controls.rs` (a notice's controls: where they sit, how the shape grows, hovering, holding and presses), `dismiss.rs` (ending a notice on request), banners (`banner.rs`) and its tests, plus the built-in notices: the "Updated" notice with its **View Changes** button, which also opens onto the [What's New](Updates.md#whats-new) page while its notes are unseen (`whats_new.rs`) |
| `live/` | the main live activity shown at rest (a tool's, or the assistant's) in `mod.rs`, up to two more hanging beside it as liquid ears (`sides.rs`), the Claude or ChatGPT mark and its moods (`agents.rs`), video downloads (`video.rs`, `downloading.rs`) and the lock screen (`lock.rs`) |
| `music/` | the music layout, beats and the dance |
| `drop_zone/`, `ask/` | the file drop well and the layout picker (`drop_zone/layouts.rs`), and the assistant's prompt card |
| `panel/` | the open panel: the row of page icons on top (`header/`), page switching (`pager.rs`), which page it opens on (`opening.rs`, `welcome.rs`), page measuring (`pages.rs`) and scrolling (`overflow.rs`) |
| `frame.rs` | per-frame preparation, the click handler and the shell painting |
| `keyline.rs` | the thin grey keyline round a floating island |
| `state.rs` | the notch's state as tools see it |
| `preview/`, `tests/` | [previews](Previews.md), and the tests that drive a whole notch with the fixtures they share |

`ui` builds an element `Env` (the style, the image store, shortcut views, the shortcut-capture prompt and the current time) and then, in order: advances (syncs tabs, uploads artwork, measures messages, notices, prompts and pages, steps every spring), paints the shell, handles a click on the shape, paints the panel, the activity, the live activity, the music, the drop well and the prompt, and returns the actions.

## Canvas and coordinates

Every notch window has a fixed logical canvas of **680 x 600 points** (`geometry::CANVAS`), centered horizontally at the top of its monitor. All notch geometry is expressed in these points, with `x = 340` as the center line and `y = 0` at the top edge of the screen. The window is transparent and click-through except over the shape, so the unused part of the canvas is invisible and inert.

## Two styles

`platform::placements` decides a style per display (see [Architecture](Architecture.md#one-notch-window-per-display)):

- **Notch** (`Style::Notch`) for a display with a hardware camera notch whose size can be measured (MacBooks). The shape is glued to the top edge and at rest covers the physical notch, so it blends into it until it grows. Its idle geometry is the measured notch size (default 185 x 32 if unknown) with a 9 point bottom radius and small 4 point **ears**: concave flares where the shape meets the screen edge, so the black body blends into the bezel.
- **Island** (`Style::Island`) for every other display, including all Windows displays. At rest it is not a floating capsule but a tiny **tab** (84 x 5 points) tucked against the top edge. When the cursor comes near, the tab swells and detaches into a 126 x 37 capsule that floats 10 points below the edge, like a Dynamic Island, and like the iPhone's it is rimmed by a thin grey [keyline](#the-keyline-notchkeyliners) while it floats.

A display change (resolution, notch size, style) is applied in place with `Notch::restyle`, which retargets every spring and snaps them so the notch does not animate across a mode switch.

## Geometry

The notch animates a small `Geometry { w, h, r, ear }`: width, height, corner radius and ear size. Four springs (`geometry::Morph`) move the current geometry toward a target. The target depends on the mode:

| Mode | Target geometry |
| --- | --- |
| Idle, Activity | the **rest geometry**: the activity if one is showing, else a tool's live activity (such as a recording timer), else the revealed music, else the idle shape |
| Peek | the rest geometry grown slightly (Notch: +18 wide, +5 tall; Island: +8 wide, +2 tall, fully rounded) |
| Expanded | panel width by top inset + page height + padding (Notch: radius 24, ears 12; Island: radius 34) |
| Drop | the drop well (below) |
| Ask | the prompt card (below) |

The panel is 372 points wide on an island. On a hardware notch it is the notch width plus 190 points of "wings", but never narrower than 372.

`Notch::silhouette` turns the current geometry into a `Silhouette`: center, top, width, height, separate top and bottom radii, ears, whether the top bleeds past the screen edge, and an optional **wave** along the bottom edge (the music dance). The notch style uses the geometry directly. The island style blends between the tucked tab and the floating capsule using the attraction value (below), and then the hug, the sideways **jolt** of an alert (see [tool notices](#tool-notices)) and the music wave are applied on top. `ui::shape` turns the silhouette into a mesh; see [Rendering and Motion](Rendering-and-Motion.md#shapes).

### The keyline (`notch/keyline.rs`)

A floating island is rimmed in grey the way the iPhone's Dynamic Island is: a 1.6 point **keyline** of grey 29 (#1D1D1D, matched to a photo of an iPhone) laid just outside the black body, so the shape keeps its edge on a dark wallpaper or over a dark app instead of melting into it. It belongs to floating: its strength is `1 - Silhouette::docking()`, so it comes in as the tab lets go of the top edge and fades out as the shape tucks back in, and the resting tab and a song or activity docked against the edge have none. A hardware notch never has one.

The band is `shape::band_around` (see [Rendering and Motion](Rendering-and-Motion.md#shapes)) round the outline the body is filled from (`Notch::body_outline`), so it follows the shape as it strains, flees and dances. It is painted after the body's shadow, so the shadow never dims it, and its strength at each height follows the body's own blackness (`Notch::blackness`), so on a Mac the open panel's keyline fades with its glass instead of drawing a grey line round clear glass. The [ears](#several-activities-notchlivesidesrs) wear it too (`Notch::paint_sides_keyline`): before any black is painted, a band goes round each ear and along the outer side of each neck's two curves (`shape::band_along`), and the black painted afterwards covers each band where the pieces meet, so the keyline runs round the whole liquid outline and never across a neck.

## Motion

Every visual change goes through springs (`ui::spring`, see [Rendering and Motion](Rendering-and-Motion.md#springs)). Changing mode calls `set_mode(mode, motion)`, which retargets the morph and all layer fades. The `Motion` kind picks spring response and damping for width and height separately (`notch/moves/transition.rs`):

| Motion | Used for | Feel |
| --- | --- | --- |
| `Open` | expanding into the panel | slightly bouncy (damping 0.74 to 0.80), height a little slower than width |
| `Close` | returning to rest | almost critically damped |
| `Dismiss` | forced collapse (before a capture) | quick, critically damped |
| `Peek` | hover growth | fast and springy |
| `Pop` | an activity, song or prompt appearing | springy |
| `Alert` | a shaking tool notice appearing | slower and bouncier (0.46, damping 0.52) |
| `Resize` | content changed size while open, or tabs changed | soft |
| `Follow` | a page growing or shrinking in place while the panel is at rest | stiff, critically damped (0.1 s), so it keeps up with the page's own spring |

Alongside the morph, a set of 0-to-1 **fade springs** decide which layers are visible: the panel, the activity, the drop well, the ask prompt, the live activity, the music, and the dance. Each layer's final opacity also depends on how far the shape has actually grown toward that layer's geometry, so content never appears before the shape can hold it and fades out as the panel opens over it.

**Haptics.** On a Mac with a Force Touch trackpad, the notch taps lightly (`platform::haptic`, `NSHapticFeedbackManager`) when the panel opens and when an ear opens under the pointer, switches in Settings and in tools tap as they flip, and a picker wheel (the Timer's hours, minutes and seconds) gives one lighter tick (`Feel::Tick`) for every row that rolls past the middle, whether dragged, flung or scrolled. macOS only plays them while a finger is on the trackpad. `notch.haptics` (**Settings › Haptics**) turns them off; Windows has none.

`Notch::is_animating` is true while any spring is unsettled, a page or the shortcut prompt is animating, or a continuous animation (the music dance, the volume meter, a beat pulse) is running. The app keeps redrawing only while it is true; a live timer instead asks to be woken once per second.

## Attraction, lean and hug

These three springs give the island its liquid, magnetic feel (`notch/moves/attract.rs`, `notch/moves/hug.rs`).

**Attraction** (island only). The distance from the cursor to everything the notch is showing right now (the tucked tab, the current shape, the docked shape and any ears, opened ears included) is mapped through a smoothstep from 24 points (no pull) to 6 points (full pull), so the shape grows only when the pointer is right next to it. The attraction spring follows that value. From 0 to 0.5 the tab swells in place from 84 x 5 to 104 x 14 while still attached to the edge; from 0.5 to 1 it detaches, drops to its floating position and becomes the capsule. Whenever something needs the capsule (an activity, a live activity, music, a peek, the panel, a drop, a prompt, or being pinned) attraction is forced to 1, and it stays there while the shape is still more than 12 points taller or (unless it is docked) wider than the resting capsule, so a closing panel or a wide notice shrinks back to the capsule before it tucks away instead of being pulled up into the edge mid-shrink. On a hardware notch attraction always rests at 1.

**Lean** (island only). While the cursor is near, the island leans toward it horizontally: the offset is 0.22 of the cursor's distance from the center line, clamped to 28 points and scaled by proximity, and the shape stretches a little with the lean. The open panel never leans.

**Hug**. When a song is revealed and the notch is otherwise idle, the shape docks against the top edge instead of floating: on an island it becomes a 176 x 24 strip with small ears; on a hardware notch it becomes wings beside the camera (the notch width plus 36 points on each side) at the notch's height. Moving the cursor toward the dock releases the hug with the same proximity curve, and the song rises into its full layout.

## Making room for menus (`notch/moves/dodge.rs`)

On a MacBook an app with many menus can run its menu titles right up to the camera, under the notch's left wing. With `notch.dodge_menus` on (**Settings › Make room for menus**), the app reads where the frontmost app's menus end (`system/menus/`, through the Accessibility API on the `notchbase-menus` thread every 0.7 seconds; without the Accessibility permission nothing is read and nothing moves) and tells each notch with `set_menu_edge`, in its own canvas points (`menus::edge_in` keeps only menus on that notch's screen that reach its window).

When the edge comes within 8 points of the shape the notch would rest at, the `dodge` spring slides the whole shape right by the width of its left wing, so the left side tucks into the camera housing and the right wing grows by as much. Whatever sat in the left wing (a notice's icon, a device glyph, the volume glyph, a live activity's mark, the song's artwork) glides under the camera to just right of it on the same spring (`Notch::lead`), and the right wing always has room for it beside the trailing part. Only one ear shows while crowded, on the right. The hover zone moves with the shape, so pointing at the menus never wakes it. When the menus are short again it flows back. Only the hardware notch style slides; the open panel, a prompt and a drop never do.

## The lock screen

`Notch::set_locked` (`notch/live/lock.rs`) puts the notch into a locked state for as long as the screen is locked:

- **A padlock.** `Activity::Lock(false)` leads the activity list, so the notch shows a closed padlock (in the left wing beside a camera, centered on an island). When the screen unlocks it becomes `Activity::Lock(true)`: 0.12 seconds later the shackle springs up and open over 0.46 seconds, overshooting a little, as the lock turns green, and 1.4 seconds after unlocking it leaves the list. The wing (or the island) then folds back into the notch the way any live activity leaves, and the open padlock rides in with it, shrinking to 60% and fading out as the wing closes (`Notch::lock_leaving_ui`), so it is swallowed by the notch instead of vanishing. Beside a song it sits in a side bubble, which leaves as side bubbles do, still open and green.
- **Nothing can be touched.** While locked the notch takes no input at all (`wants_input` is false, the pointer is ignored, clicks fall through to the lock screen), never peeks or opens, ignores `open_page`, holds and drops, and puts away the open panel. A Claude prompt never shows while locked: the card waits (`follow_card` treats a locked notch as having none) and comes back once you're in. Notices and live activities (the song, Claude working, a timer, charging) still show.

**On a Mac's lock screen.** macOS draws the lock screen above every app window. With `notch.lock_screen` on (**Settings › Show on the lock screen**), each notch window is moved into a window-server space that sits above the lock screen as the screen locks (`NotchWindow::follow_lock`, checked every frame in `app/frame.rs`; `platform/macos/lock_screen.rs`), so the notch stays visible there and you watch the padlock open as your password is accepted. A window that has been in that space never receives drags again, even once it is back in its own space, and files dropped on the notch would fall through to the desktop. So once you're in, the padlock has finished opening and the notch has folded it away (`Notch::above_lock_screen`), the window is sent home, the space is hidden and destroyed, and the notch window is replaced with a new one (`replace_spent_notches`). The swap waits until the notch is at rest (closed or showing a prompt card, with no notice, and its shape settled) or 1.2 seconds after it last moved, whichever comes first; an open panel keeps the old window up until it closes. The new window opens before the old one goes and starts where the old one stopped: before its first frame it is fed the current activities and song and takes over the old one's prompt, song reveal and hover arming (`Notch::take_over`), and once that first frame has measured what it shows, every spring is snapped and the frame is painted again before the window appears (`Notch::settle_in`), so nothing pops in a second time and the swap can't be seen. The space only exists while the screen is locked. It uses private SkyLight calls (`SLSSpaceCreate`, `SLSSpaceSetAbsoluteLevel`, `SLSShowSpaces`, `SLSHideSpaces`, `SLSSpaceDestroy`, `SLSSpaceAddWindowsAndRemoveFromSpaces`, `SLSMoveWindowsToManagedSpace`, `SLSCopySpacesForWindows`, `SLSGetActiveSpace`), loaded with `dlopen`, and does nothing if they're missing; a macOS update could change them. `SLSSpaceAddWindowsAndRemoveFromSpaces` returns a non-zero value when it works, so its result is ignored. The setting is read each time the screen locks. Windows has nothing like it, so there the padlock only shows as you come back.

**A notch opened while the screen is locked.** The app keeps the last reading (`App::screen_locked`), and `sync_notch_state` hands it to every notch each time the windows are rearranged, so a notch that opens while the screen is locked starts locked: it shows the padlock, goes above the lock screen and opens as you come back. With **All displays** on this happens every time the display sleeps on a Mac, which includes closing the lid: a sleeping display is not in the list of displays, so every notch window is retired within a second and a new one opens as the display wakes. A window retired while it is above the lock screen leaves that space first (`retire_notches`), so the space is still destroyed and the new window gets a fresh one.

## Pointer state machine

`notch/pointer.rs` drives hover behaviour from the cursor each tick:

1. **Idle or Activity.** When the cursor rests in the hover zone (the shape's bounds plus an 8 point margin, reaching the screen top) for **150 ms**, the island is fully drawn out, and `notch.open_on_hover` is on, the notch goes to **Peek** and starts a dwell timer (`notch.hover_delay_ms`, 300 ms by default). Sweeping past on the way to a browser tab never peeks, and neither does resting on the [controls](#tool-notices) of a tool notice. With `notch.open_on_hover` off it never peeks and opens on a click instead: while the pointer rests in that same hover zone with the island fully drawn out, the notch takes the pointer, and a click anywhere in the zone opens it straight to **Expanded**, onto the same page as clicking the shape (see below). Moving away without clicking hands clicks straight back to whatever is underneath and leaves it at rest.

   With `notch.wake_at_edge` on (the default), an island doesn't react to a pointer passing further away. It only wakes from the thin strip above a browser's tab buttons: the pointer has to be in the top 7 points of the screen and within 16 points of what it's showing (24 points while it's fully closed, tucked away or docked flat, so it reaches out a little further along the edge), or touch the top 4 points of the screen anywhere within reach of it. A pointer on a tab's close or new-tab button, even right under it, never wakes it. Once awake it draws out, leans and can peek as usual, and it stays awake while the pointer is within 70 points of it. Once the pointer wanders further away it goes back to sleep, and so does closing the panel or a peek by moving away, so a browser tab right below the notch can be clicked straight after. Moving over the browser tab strip below the edge leaves it untouched, and the ears beside it don't open under a sleeping pointer either. A song or activity docked against the top edge lifts off under the same rule. A Mac's real notch never sleeps like that, since nothing sits under it, but the same setting narrows where it opens from: with it on, the notch only peeks (or, with opening on hover off, only takes the click) while the pointer is on the notch itself, the camera housing's own rectangle, not the 8 points beside it or the 4 below, and not the wings an activity or a tucked song add (`Notch::wake_zone` in `notch/zones.rs`). A pointer just below still lets a tucked song come down. With the setting off it opens from the whole hover zone as before.

   Hold down any key, or press any mouse button, with the pointer near the notch and it takes fright: it flows sideways out from under the pointer like liquid pushed by a magnet, reacting from further away and pushing harder the closer the pointer gets. Its surface dents in where the pointer presses, ripples while it's scared, and stretches into a thinning tail as it slides, and it keeps running the same way if you follow it. While the key is held it doesn't wake, peek or open its ears, and clicks go straight through to whatever it was covering, like a browser's new-tab button. Let go and it flows back, waiting for the pointer to leave before it peeks again. A mouse button only scares it when the press starts near it, so clicking a tab right under it works in one go while a file dragged in from elsewhere still drops onto the shelf, and pressing on the notch itself (a peek, an ear's button) never scares it. The open panel ignores all of this, and so does typing into notchbase itself. Turning off `notch.flee_from_keys` (**Settings › Move away for keys and clicks**) makes it stay where it is for held keys and for mouse presses alike; clicks beside it still go through to what is under it.
2. **Peek.** The peek is the main view: a song that's around comes up in it (see Reveal below), so hovering the notch shows the player pill first. Holding on it past `notch.hover_delay_ms` starts the **surge**: over 380 ms the black of the pill strains outward, growing up to 4.5 points all round with smooth liquid lobes (up to 8 more points, spaced along the edge and drifting in opposite directions) and a fine tremble that builds toward the end, as if it's trying to break out. When the strain peaks the notch opens to **Expanded**, and the surge sinks back into the growing panel on a spring; letting go early sinks it back into the pill the same way. The pointer has to be more or less still for this: moving more than 12 points from where it settled starts the hold (and the surge) again, so a restless pointer never opens the panel. If the pointer leaves, the notch returns to rest; if it leaves for one of the ears, the notch stays awake so the ear opens instead. If it moves onto a notice's controls, the peek drops back to the notice at once, so the button can be pressed.
3. **Expanded.** The panel stays open while the cursor is inside the expanded zone (the panel bounds plus a 44 point margin, reaching the screen top) so a pointer that wanders a little off the panel doesn't close it. Switching to a shorter page shrinks the panel away from a pointer near its bottom, so after a switch it also stays open while the pointer is anywhere above where it was then, within the panel's width plus the margin (and down to 44 points below that spot); once it is back inside, the usual zone applies again, and moving on down or out to the side closes it. After the cursor leaves, a grace period (`notch.close_delay_ms`, 220 ms by default) lets it come back before the panel closes. On the Settings and Notifications pages the pointer leaving never closes it; pressing the gear returns to your tab, after which it closes as usual.

Clicking the shape opens it immediately, except while a sticky tool notice is showing: then the click dismisses the notice, which ends at once. A click on one of a notice's controls goes to the tool and opens nothing. While this version's notes are unseen, opening goes to the What's New page, ahead of everything else (see [Opening onto What's New](#opening-onto-whats-new)). Otherwise, if the shelf holds anything and Shelf is one of the tabs, opening goes straight to the Shelf page. Otherwise, if a song is known (playing, or paused but still shown), `music.open_to_player` is on and Media is one of the tabs, opening goes straight to the Media page. `set_pinned(true)` keeps the panel open regardless of the pointer; the app pins the notch while a shortcut is being rebound or a tool text field has focus. `collapse()` forces the notch closed (used before a capture and by a tool's `Collapse` request) and disarms hovering until the cursor has left, so the notch does not immediately reopen under a cursor that is still on it. An unknown cursor position (for example while a capture overlay has the mouse) counts as outside.

The `notch.*` keys are described in [Configuration](Configuration.md).

## Zones

`notch/zones.rs` defines the rectangles the app and the state machine test against:

- **hover zone**: where hovering starts a peek.
- **expanded zone**: where the open panel stays open.
- **input zone**: where the window stops being click-through. It is the current silhouette and any ears, plus the open panel or prompt, plus 4 points. Outside it, clicks go to whatever is behind the notch. At rest (Idle) the notch takes no clicks at all, even on its shape, so a docked song or activity never steals a click meant for a browser tab underneath; it takes input once it peeks.
- **catch zone**: where dragged files are caught. It reaches from the screen top well past the resting shape (110 points to the sides, 90 below) and includes the open panel, so you can drop onto the notch without aiming precisely. Only a drag that came in from outside the zone is caught: a press that starts inside it (a window's maximize button right beside the notch) is left alone until it lets go, so the window under the notch gets its click. On a Mac a press that starts inside still counts once the drag carries files (`app/shelf/drops.rs`). Once the drop well is showing, the zone becomes the well plus a 28 point margin.

## Activities

An activity (`notch/activity/mod.rs`, with tool notices in `notch/notice/`) is a short-lived notice that grows the notch at rest. `ActivityKind` has four kinds:

| Kind | Started by | Duration |
| --- | --- | --- |
| `Tool(ToolNotice)` | a tool's `Notice` request (`show_notice(slot, notice)`) | the notice's own duration, or until dismissed if it is sticky |
| `Message(String)` | `show_message`, for errors and hints | `notices.message_ms` (3.5 s) |
| `Indicator(Indicator)` | `show_volume`, `show_brightness` | `notices.volume_ms` or `notices.brightness_ms` (1.6 s) |
| `Device(DeviceNotice)` | `show_device` | `notices.device_connected_ms` (3.2 s) or `notices.device_disconnected_ms` (2.2 s) |

While an activity is live the notch is in **Activity** mode and its rest geometry is the activity's geometry. When it expires the notch closes back to Idle. An activity that starts while the panel is open, a drop is hovering or a prompt is showing waits underneath and becomes the rest state when that ends. A new activity replaces the current one: if the old one is on screen it stays drawn and fades out (`Activity::leaving`) while the new one fades in after it (`Activity::swap`), so a notice's pop starts unseen instead of snapping its icon small. The same notice sent again while it shows keeps its place and measured size, gets its time back and gives a small nod (a dip of the pop spring) instead of popping in afresh. Notices, messages and prompt cards are measured on their first frame; while the shape is still on its way, measuring only moves the target and keeps the motion it started with (`Notch::remeasured`), so an alert keeps its springy `Alert` arrival and a card its `Pop`.

On a hardware notch, activities lay their content out in **lanes** on either side of the camera (leading and trailing), optionally with a row below the notch. On an island they lay out inside the capsule, which widens to fit its measured content. Some activities "pop": the leading element starts at 40% scale and springs to full size as the activity fades in (tool notices that ask for it, and a device connecting).

**Messages** are measured text, wrapped at 304 points and re-wrapped to balance the lines. On an island the capsule is 126 to 340 points wide; on a hardware notch the text sits below the camera row. A message short enough to fit the resting capsule ("Key copied") needs no growth at all, so its words show as soon as the capsule is out.

### Tool notices

A tool notice (`ToolNotice`, `notch/notice/mod.rs`) is an SDK `NoticeNode` plus the tool's slot. It has a **leading** element, a **trailing** element, an optional **below** element, optional **controls**, a `NoticeSize`, a duration in milliseconds, and flags for `pop`, `shake`, `banner` and sticky. All four parts are element trees painted by the element renderer (see [Rendering and Motion](Rendering-and-Motion.md#tool-elements-uielement)); an element can be `adaptive`, choosing a different tree for the Notch and Island styles. See [tools/Surfaces.md](tools/Surfaces.md) for the tool author's side.

**Sizing.** The first frame after a notice arrives, its leading and trailing parts are measured, and the below part and the controls are measured wrapped at 304 points. The notice geometry then grows to fit:

| | Small | Medium | Large |
| --- | --- | --- | --- |
| Hardware notch: minimum wing on each side of the camera | 64 | 76 | 92 |
| Island: minimum capsule width | 176 | 236 | 236 |

On a hardware notch each wing is at least wide enough for the wider of the two parts plus a 10 point clearance from the camera; on an island the capsule is at least as wide as both parts plus a 12 point gap. With a below part, the notch grows downward by its height plus padding (and is at least as wide as it), and the island grows from 37 points tall to fit it under the lane.

**Banners.** A notice with `banner` is laid out by `notch/notice/banner.rs` instead of in lanes:

- **Block.** The leading element sits on the left. The trailing and below elements stack beside it, left-aligned, 10 points from it with 2 points between them. The text parts are measured at up to 260 points wide. The whole block is centered in the body.
- **Island.** The capsule is the block plus 12 points above and below, at least 37 tall and 180 wide. Its corner radius is half its height, up to 30. The side padding is set so the leading element sits concentric with the rounded end (at least 14 points).
- **Hardware notch.** The banner hangs below the camera: 6 points under the camera row and 12 below the block, with 18 points of side padding and 18 point corners. It is at least 28 points wider than the camera on each side.
- **Presets and pop.** The size presets don't apply. The leading element pops like any other notice.

**Shake.** A notice with `shake` starts with `Motion::Alert` instead of `Motion::Pop`, and kicks the `jolt` spring sideways (a very low-damping spring, response and damping 0.16, with an initial velocity of 420 points per second, alternating direction on repeated alerts). The jolt offsets the whole silhouette horizontally, so the notch wobbles side to side and settles. An alert that arrives while the panel is open, a drop is hovering or a prompt is showing doesn't kick it, since nobody would see the notice shake. The bundled [Alerts](Alerts.md) tool uses this.

**Sticky.** A notice with a duration of 0 is sticky: it stays until the notch is clicked (the click dismisses it instead of opening the panel) or the tool sends `DismissNotice`. `dismiss_notice(slot)` only ends the notice if it belongs to that tool.

**Dismissal** (`notch/notice/dismiss.rs`). Being dismissed is not the same as running out of time. `dismiss_notice(slot)` and the click on a sticky notice both end the activity on the spot through `end_activity()`, the same ending `expire_activity` reaches when the time is up: the expiry is cleared and the notch closes to rest. Nothing is left to expire, so a pointer resting on the notice's controls cannot hold a dismissed notice (see below), and it does not come back.

**Controls** (`notch/notice/controls.rs`). A notice can carry one more element tree, `controls`, and it is the only part of a notice that takes presses. The Screenshot tool uses it for its **Annotate** button (see [Annotate](Annotate.md)), and the app's own "Updated" notice for **View Changes** (see [the app's own notices](#the-apps-own-notices)).

- **Inline on an island.** When the notice has no below part, is not a banner, and the controls are no taller than the capsule less 5 points above and below, they are tucked into the trailing end of the capsule, which stays 37 points tall and widens to fit them. The controls sit as far from the capsule's end as from its top and bottom, so a pill sits evenly in the rounded end, and the trailing element moves over to end 10 points before them.
- **In the right wing beside a camera** (`Notch::splits`). On a hardware notch, a notice whose controls are one button (an `adaptive` one counts by its notch variant) no taller than the camera housing, with no below part, not a banner and no app menus crowding the notch, puts that button in the right wing, level with the camera and 8 points from the shape's end (`WING_INSET`), and moves the trailing element into the left wing, 8 points after the leading one (`SPLIT_GAP`). Both wings take the width of the wider side (`split_wings`), and the shape only grows taller if the button needs 5 points under it (`SPLIT_MARGIN`). The notice never grows wider than the panel it opens into (`panel_width`: the camera plus 190 points, at least 372). When even wings would, it keeps the panel's width and leans toward the button: the left wing keeps just the room its words need and the right wing takes the rest, and the offset (`notice_shift`) rides on `Morph::shift`, a spring that moves the whole silhouette, its content, the hover zone and the panel's stage, animated with the width's spring by `retarget` and `follow_target`, so the shape glides back over the camera as the panel opens. Only when the words and the button can't share that width, or the menu bar reaches the notice's own left edge (`Notch::menus_reach`, checked against the split shape so the dodge and the split never feed each other), does the button fall back to the row underneath; `follow_split` retargets the shape when that decision changes while the notice shows. Screenshot's **Annotate** and the "Updated" notice's **Changes** sit there, so neither leaves a black box hanging under the camera around one button.
- **A row underneath.** In every other case (a hardware notch where the button can't take the right wing, a below part, a banner, tall controls) the controls are centred in a row under the content. The shape grows by their height plus an 8 point gap, and by 10 more points of padding when the content has no below part and is not a banner (those end in padding of their own). It is at least as wide as the controls plus 14 points on each side. On a hardware notch the corner radius is at least 14 and the ears at least 6; on an island the radius is half the height, up to 30. Tests check the row under camera housings from 160 to 200 points wide and 30 to 38 tall: it starts at least 6 points below the housing and ends at least 8 above the bottom edge.
- **Presses.** The controls are painted by the element renderer with the surface `Surface::Notice`, and a press leaves `Notch::ui` as `Action::Tool(slot, Surface::Notice, handler, value)` (or as an action of the app's own, for [a notice the app posted](#the-apps-own-notices)). They take presses only while the notice is the live activity and more than 60% faded in, the screen is not locked and the notch is not a pinned preview. A press never opens the panel. A click anywhere else on the notice still opens it, and resting anywhere else still peeks.
- **The controls zone and the pointer.** The zone is the controls' rectangle plus 6 points all round (`controls_zone`, `CONTROLS_REACH`), the same on an island and under a hardware notch, inline or underneath. It exists only while the notice is the showing activity and has controls. While a calm pointer is in the zone:
  - the notch never starts a peek, and a peek that was already up drops back to the notice (`pointer.rs`);
  - the notice is **held**: each tick pushes its expiry to at least one second from now (`hold_hovered_notice`, `HELD_FOR`), so it never vanishes under a pointer on its way to the button. A second after the pointer leaves, or at its own time if that is later, it goes as usual. The hold only ever pushes back an expiry that exists, so it has no effect on a notice that has been dismissed.

  Everywhere else on the notice the pointer is treated as on a plain notice, also level with a button hung underneath: resting there peeks, a click opens the panel, and the notice leaves on time. A locked notch and a notch fleeing from a held key ignore the zone.
- **Dismissed from the controls.** When a tool sends `DismissNotice` for its notice while the pointer is on its controls (the usual case: the answer to a press, as with Annotate; the pointer is the one the last tick saw), or a sticky notice is clicked inside its controls zone, the notch also disarms hovering (`wait_for_the_pointer_to_come_back`): the pointer the notice was dismissed under wakes nothing, neither a peek nor the panel, until it has left the notch and come back. A dismissal with the pointer anywhere else, and a click on a sticky notice outside the zone, end the notice and leave hovering as it was.
- **Arriving under the pointer.** A notice with controls disarms hovering when it starts (`wait_for_the_pointer_to_come_back`): a pointer that was already resting on the notch neither peeks nor opens the panel over the button, until it has left the notch or been on the controls. If the notch was peeking, it drops to the notice with the notice's pop. A notice without controls leaves a peek alone, and the panel opens as before.
- **With opening on hover off**, a control still takes its press; a click beside it opens the panel.

#### The app's own notices

A notice needs a slot, and tools are numbered from 1 (a preview's sample notice uses 0). The app keeps the top of the range for what it shows itself, through the same `show_notice` and `set_activities` a tool's request ends in:

| Slot | Constant | Used for |
| --- | --- | --- |
| `u16::MAX` | `UPDATER` (`app/updates.rs`) | the **Updating** live activity |
| `u16::MAX - 1` | `AGENTS` (`app/assistant/agents.rs`) | the assistant's "done" notice |
| `u16::MAX - 3` | `whats_new::SLOT` (`notch/notice/whats_new.rs`) | the "Updated" notice |

The **"Updated" notice** is the one with a control. `whats_new::updated(version)` builds it with the SDK builders, exactly as a tool would: a pearl spark badge leading, an `adaptive` trailing part ("Updated" beside a camera, "Updated to notchbase 0.14.0" on an island), a pop, `NoticeSize::Large`, 8 seconds, and an `adaptive` button as its controls: **Changes** beside a camera, **View Changes** on an island. It has no below part and is not a banner, so an island tucks the button into the end of its 37 point capsule, and beside a camera the badge and "Updated" take the left wing while **Changes** ends the right one. It is not sticky, so a click beside the button opens the panel.

No tool owns the slot, and the tool host drops an event for a slot it does not know, so the press is translated inside the notch: `activity_ui` passes a notice's presses through `whats_new::pressed`, which turns any press on that slot into `Action::ViewChanges`. Every other slot's presses pass through untouched. The app posts the notice from `resumed` once the tools and the assistant have started, through `Notch::show_updated`, which leaves a message that is already showing in its place (see [Updates](Updates.md#whats-new) for when, and for what the action does), and the `updated` [preview](Previews.md) pins the very same notice. Tests in `notch/notice/tests/updated.rs` press it in both styles and check its shape under five camera housings.



### The live activity

A tool can also provide a **live** view: a leading and a trailing element shown at rest while nothing else is (`notch/live/mod.rs`). The Record Screen tool uses it for a red dot and the running recording time. The app gathers every current activity in order (video downloads, then the assistant's progress, then tools' live views, then the updater's ring) as `bridge::Activity` values and passes the list to every notch with `set_activities`. The notch puts the padlock first and the app's downloads ahead of everything else (`combine_activities`), so a download leads whenever the screen is unlocked.

An activity is `Activity::Tool(slot, LiveNode)`, painted by the element renderer, or `Activity::Agent(AgentLive)`, which the notch also paints itself (`notch/live/agents.rs`): the Claude spark or the ChatGPT knot (`ui/brand.rs`) and a word or a time, with a **mood**:

| Mood | Mark | Right side |
| --- | --- | --- |
| Thinking | turns slowly | the time since the turn began, in the secondary color |
| Doing | spins faster and breathes | what it is doing: Running, Editing, Reading, Searching, Browsing, Delegating, Planning, Using tools |
| Waiting | stands still, in yellow | "Needs you", in yellow |

Several sessions at once show one mark with a count beside it, timed from the oldest. The mark keeps its own turn (`agent_mark::Spin`) and eases from one pace to the next over about half a second, so a change of mood, which comes with every tool call, never jumps it to a new angle; the Agents page keeps one for each run. When the words beside the mark change (the clock to a verb, one verb to the next, "Needs you"), the old words roll up 7 points and fade out as the new ones roll in from below (`agents::Said`); the clock ticking over a second is not a change of words.

- **Geometry**: on a hardware notch each wing is at least 56 points, or the wider part plus the camera clearance; on an island the capsule is at least 116 x 34 points, or both parts plus a 16 point gap. The parts are re-measured each frame, and the notch resizes if a width changes by more than half a point (for example when a timer goes from 9:59 to 10:00). A resize while the shape is still moving keeps the spring it is moving on (a pop stays a pop, a dismiss stays a dismiss); at rest it resizes with `Motion::Resize`.
- **Swapping**: when the leading activity changes to a different one (another tool, the assistant), its content fades in from nothing on a 0.3 s spring instead of appearing at full strength, while the old one fades out under it. A live activity that comes or goes while a notice is showing leaves the notice's motion alone.
- **Leaving**: an activity that ends (a finished run, a stopped recording, a timer that runs out) keeps its content while the wings fold back, fading it out on the same quick spring the song and notices use, instead of vanishing on the frame it ends (`live_leaving`). The padlock leaves through its own fold (see [The lock screen](#the-lock-screen)).
- **Visibility**: it shows in Idle and Peek, and yields to a regular activity while one is live.
- **Controls**: if the tool gave its live activity [`controls`](tools/Surfaces.md#live-activity) (a meeting's join and × buttons, say), resting the pointer on the main shape opens them at its trailing end: the shape widens by the controls plus 8 points, the trailing element slides over, and the buttons fade in on the ears' hover spring (`live_hover`). They take presses once more than half open and the activity is more than 60% faded in, never while locked or in a preview, and a press goes to the tool as `Action::Tool(slot, Surface::Live, ..)`. The controls zone (their rectangle plus 6 points) works like a notice's: a peek drops back to rest on it so the dwell never opens the panel under a button, the window takes the pointer there even at rest, and after a press hovering is disarmed until the pointer leaves, so hiding a meeting doesn't open the panel under the cursor.
- **Hugging**: on an island a live activity docks to the top edge at rest, 24 points tall, like a playing song does, and comes loose into the capsule once the pointer wakes it from the strip above the tabs. While an ear is hovered open the main shape stays loose, so reaching for the far end of the ear (its stop or cancel button) never docks the shape and pulls the ear away.

### Several activities (`notch/live/sides.rs`)

The notch shows up to **three** activities: one in the middle and up to two **ears**, the first on the right and the second on the left.

- **Who leads**: music takes the middle whenever a song is revealed and anything else is live; the song's compact view (artwork and bars, docked on an island) stays, and every activity becomes an ear. A video download is the exception: while one is first in the list the song never takes the middle from it (`Notch::music_leads`), and the bottom edge stops dancing under its line of light (`Notch::dances`). With no music the first activity leads and the next two become ears. Anything past three waits.
- **Budding**: each ear has its own spring. A new ear grows out of the end of the main shape, starting at 55% of its size, and settles 6 points away; a finished one shrinks back in before it is dropped. An ear keeps its side while it animates out, so the others never jump.
- **Liquid necks**: an ear is never just a separate circle. On a floating capsule it is joined to the capsule's end by a metaball neck: two cubic curves between the end cap and the ear whose spread shrinks as they part, pinching to a waist at rest and letting go completely 14 points past touching. Docked on an island, or on a hardware notch, the ears are tabs hanging from the top edge, and a web joins them to the main shape along the top, its underside rising in a rounded curve as the gap grows. Each end of that curve sits on its own shape's outline and leaves it along that outline (`Blob::side_at`), so when an opened ear's corner starts rounding off higher up, the web flows into it instead of hanging past it as a pointed tail, and the web's sides tuck a point into each shape that bleeds over the top edge, so no hairline shows where the anti-aliased edges would otherwise meet. As an island docks or comes loose, each ear follows it continuously (`Silhouette::docking`): the bubble stretches up toward the edge, its top corners straighten and its ears grow in, instead of switching from bubble to tab in one frame. On a floating island the [keyline](#the-keyline-notchkeyliners) runs round each ear and its neck.
- **Hardware notch**: the main activity keeps the wings either side of the camera, and the ears hang beside the wings at the full notch height, so nothing ever sits under the camera. The layout is checked against notches from 160 x 30 to 200 x 37 points, including the 13-inch MacBook Air's (about 190 x 33).
- **Content**: an ear shows the activity's leading element (a dot, a ring) or the assistant's mark, and fades in only once the ear is nearly full size.
- **Hovering an ear**: resting the pointer on an ear swells it by 16% (the neck to the main shape thickens with it) and stretches it outward into a small pill that shows the activity's trailing element (a timer, the assistant's status) and, if the tool gave its live activity [`controls`](tools/Surfaces.md#live-activity), those controls: pause, resume, cancel, stop. An ear only opens for a pointer that has woken the notch at the top edge, the whole opened pill (out to its last button) counts as the ear, and it takes clicks once it is more than half open, so a pointer passing over it never steals a click, and hovering an ear never peeks or opens the main shape. Moving away folds it back in on the same spring.
- **Swapping places**: when the song tucks away and an ear becomes the main activity, the ear flows back into the shape while the shape eases to its new width (the docked width has its own spring), and the content cross-fades in place. Nothing jumps between frames; a test holds every frame's width change under 4 points.
- **Input**: the ears are part of the input zone. Clicking an opened ear whose tool has its own page (a timer, for instance) opens the panel straight onto that tool's page; its buttons still take their own clicks. Clicking an ear without a page opens the panel like the main shape; clicking the assistant's ear, or the assistant's live activity itself, opens the Agents page.
- **Timers**: if the live view contains a timer element, the notch wakes exactly at the next second boundary and redraws, instead of animating continuously.

### Volume indicator

`Notch::show_volume` (`notch/activity/volume.rs`) shows the system volume when a volume key is pressed (see [Volume and Media Keys](Volume-and-Media-Keys.md)). On an island it is a 210 x 37 capsule with a speaker glyph, a liquid meter track and the percentage; on a hardware notch the glyph and the value sit in the lanes beside the camera with the meter below. Further key presses while it is showing move the meter smoothly instead of restarting the activity. The bar always leaves room for "100", so it keeps its length when the number gains a digit. If a song is playing, the volume appears as a **strip** under the song instead (below).

`Notch::show_brightness` shows the display brightness the same way, with a sun glyph in place of the speaker. Both are one `Indicator` (`Volume { volume, muted }` or `Brightness(level)`) sharing the activity, the meter and the strip, so a brightness key pressed while the volume is showing takes over the same capsule: the glyph and number swap and the meter jumps to the new level instead of sliding to it.

### Device indicator

`Notch::show_device` (`notch/activity/device.rs`) shows a Bluetooth device connecting or disconnecting: a glyph for the device kind, its name, and its status, which is a battery ring (green, orange at 20% or below, red at 10% or below) when the level is known, and otherwise "Connected" or "Disconnected". A battery update for the device that is already showing refreshes the ring in place. With `bluetooth.indicator` off nothing is shown, and with `bluetooth.battery` off the battery is left out. See [Bluetooth](Bluetooth.md).

## Music

`src/notch/music` makes the notch a small music player and a visualizer. It is fed by `Notch::set_now_playing` and `Notch::set_music_levels` every frame; see [Media and Music](Media-and-Music.md) for where those come from.

- **Reveal.** A noteworthy change (a new title or artist, or play/pause) reveals the song for 4 seconds. Bringing the cursor near the dock summons it, renewed every frame the cursor is near, so it tucks away 0.3 seconds after the cursor leaves. While revealed, the rest geometry is the music layout: on an island a 250 x 48 capsule with artwork, title, artist, remaining time and level bars; on a hardware notch the artwork and bars sit in the lanes beside the camera and the title line drops below. The timings are `music.reveal_ms` and `music.hover_reveal_ms`; with `music.in_notch` off, songs are never revealed at rest (the Media page still works). When the player stops reporting a song while it shows (it quits, or a paused song outlives its 3 second linger, which is shorter than the reveal), the song is concealed and the last one drawn fades out as the wings fold (`music_leaving`) instead of blinking out. On a hardware notch a song tucked beside the camera folds from where it sits (`fold_from_the_tuck`): the shape takes over the tucked size before it shrinks, so it never sags back toward the title line's depth while the tuck lets go. A reveal or a conceal while the panel is open, a drop shows, a prompt is up or a notice holds the shape leaves that motion alone (`Notch::remeasured`), since the song only changes the shape at rest.
- **Dance.** While a song is playing, the bottom edge of the shape ripples with the music. Six spectrum bands drive a `notch::liquid::Liquid`: one underdamped spring per band (so a hit overshoots like liquid), seven Gaussian ripples placed across the edge, each tied to a band, with a slow drift and sway. The depth is 8 points on a notch and 6.5 on an island, reduced when docked. The dance keeps going behind other states (an activity, a live activity, a prompt, a drop) as long as music is playing, so the notch never goes stiff mid-song. It can be turned off with `music.dance` in [Configuration](Configuration.md).
- **Beats.** Changes are acknowledged with short pulses on the artwork: a play or pause pulse with a glyph and ring (650 ms) and a nudge when you press next or previous (380 ms).
- **Song changes.** A new title or artist hands the words over (`ui::handover`): the old title, artist and remaining time slide out the way you skipped and fade while the new ones slide in after them (450 ms). The cover (`ui::cover`) doesn't flash the grey placeholder while the next artwork loads: the old cover stays until the new one arrives (up to 1.2 s, then the note), and the new cover dissolves over it with a slight settle while the bars and ring ease to its colour over 0.4 s. During a pulse the artwork is drawn as a warped 18 x 18 mesh, which makes it ripple. The level bars and the pulse ring take the most vibrant color in the artwork. Pausing lets the bars settle on their springs instead of dropping flat in one frame.
- **Anticipation.** Media controls answer instantly. `Notch::anticipate` flips play/pause or nudges immediately, and for 1.5 seconds ignores a stale report from the player that still says the old state. When the player confirms, the expectation is cleared.
- **Strip.** A volume change while music is playing grows a 22 point strip under the song with the volume row, instead of a separate volume activity. It does so every time a song is playing, even while Claude or a tool has a live activity (the song takes the middle and they move to the ears) or a notice is up (the notice gives way), so the song is never missing while you change the volume. It lasts `notices.volume_ms`; when it expires the song is concealed again, and the strip stays drawn (`strip_gone`) so it folds away with the shape instead of vanishing. A brightness change uses the same strip, for `notices.brightness_ms`.
- **Clock.** The remaining time ticks once per second; the notch asks to be woken exactly at the next second boundary rather than animating continuously.

## Drop zone

When files are dragged over the catch zone, the app calls `set_drop_hover(Some(count))` and the notch enters **Drop** mode (`notch/drop_zone/mod.rs`): a well of blue-tinted glass with a slowly pulsing glow (1.8 s period), a tray glyph that bobs, and the prompt "Drop to add to Shelf" with the file count. Dropping adds the files to the shelf and opens the Shelf page; cancelling returns to rest. See [Shelf](Shelf.md). The same well holds the window layout picker and a dragged video link's Video and Audio tiles; whichever it showed last (`WellFace`) is what it fades out with, so the grid or the tiles never turn into the shelf prompt as the notch closes.

## Ask prompts

When Claude Code or Codex needs an answer, the app calls `show_ask(Some(ask))` and the notch enters **Ask** mode (`notch/ask/`). The prompt card is 360 points wide on an island, or the notch width plus 160 points of wings (at least 360) on a hardware notch, and its height is measured from its text:

- a source line with the provider, the project (and agent type, if a subagent asked) and the question's short header, then "2 of 3" when several questions are asked together, or "+N more" when more prompts are waiting,
- the title (the command's question, or the question itself) in the headline font, up to three lines,
- an optional detail (for example the command to run) in a monospaced well, up to three lines,
- for a question, one full-width row per option with its label and, beside it, its description. A single-choice option answers with one tap (or moves on to the next question); a multi-choice question shows a check circle on each row and a **Next** / **Done** button that stays dim until something is ticked. **Back** returns to the previous question with its answer kept,
- the buttons: **Deny** / **Allow** for permissions, plus **Always allow** when Claude offers a rule for it; "Answer in Claude" / "Answer in ChatGPT" sits on the left when there is room, for typing your own answer. When the prompt can only be answered in the assistant itself, that is a single button.

`notch/ask/steps.rs` (`Answering`) keeps which question is showing and what has been picked, and starts over when a prompt with a new id arrives; `notch/ask/offers.rs` paints the option rows, `notch/ask/card.rs` the card and `notch/ask/mod.rs` its footer, whose buttons and link come from the shared `ui::buttons` (`crates/paint/src/buttons.rs`, which the installer uses too).

If a drop is in progress the prompt waits until it ends. A new prompt with a different id replaces the old layout; answering returns the notch to rest or to the next prompt. A card that leaves for good (answered, or one that went away) keeps what it last showed, no longer clickable, and fades it out where it stood while the shape closes over it, instead of going blank on the frame it is answered (`Shown`, remembered each frame the card is up). See [Assistant](Assistant.md).


## The open panel

When Expanded, the notch paints a row of page icons and the gear along its top, and one page below them.

### Tabs

Tabs are dynamic. The app passes the current `bridge::Tab` list (a `Page`, a `key`, a title and an icon) in `PanelData` every frame; `sync_tabs` notices when it changed. A tab's page is a core page (`Page::Media`, `Tools`, `Shelf`, `Stats`, `Agents` while an assistant is chosen, or `Sound` when `layout.tabs` lists it; the default header leaves it out because the Media page holds the mixer) or `Page::Tool(ToolSlot)` for a tool that has its own page. The order comes from `layout.tabs` in `config.json`, which lists core pages and tools whose manifest asks for a header tab with `.header_tab()` (the bundled Calendar does) in any order; header-tab tools it doesn't list follow, in tool order (see [Architecture](Architecture.md#tabs)). Other tool pages open from their tile on the Tools tab. `Page::Settings` is not a tab; the gear opens it.

The page the notch opens to is the tab whose key is `notch.start_page` (`sound` without a Sound tab opens Media, which holds the mixer), falling back to Tools and then to the first tab. If the tabs change and the current page is no longer among them, the pager falls back to the first tab (Tools, Settings, Notifications, the Library, Find and What's New are always allowed to stay).

### Opening onto What's New

`notch.start_page` is only where the pager starts. After that the panel reopens on the page it last showed, unless one of the per-open rules in `notch/panel/opening.rs` picks another: a filled Shelf, a known song, the page of the live activity that was clicked. [What's New](Updates.md#whats-new) adds one that goes first (`notch/notice/whats_new.rs`):

- **The flag.** The app says whether this version's notes are unseen in `PanelData.app.news`, and `advance` copies it to `news_due` every frame, the way it keeps `shelf_filled`. A hover opens the panel from `tick`, where there is no `PanelData` to ask.
- **The rule.** `opens_to_start` asks `opens_to_news` before anything else. While the notes are due and the notch is at rest, peeking or showing an activity, it shows `Page::WhatsNew` and ends the "Updated" notice if that is what is showing, so the notice is not there again when the panel closes. Any other notice is left to wait underneath as usual. This is what a hover that dwells into the panel and a plain click both reach, so the page outranks the Shelf and the song.
- **What it leaves alone.** A click on a live activity that has a page of its own keeps that page (`opens_on_click`), and `open_page` never passes through the rule, so a drop still opens the Shelf and an ear its tool. A locked notch and a pinned preview never open by themselves at all.
- **A page that passes.** What's New is not a place the panel should come back to. When the panel is hidden and the notch is no longer expanded, `never_reopen_into_a_passing_page` (`panel/header/corners.rs`, called from `panel_ui` every frame) moves the pager from What's New to `way_back()`: the tab it came from, or the one the lens rests under. So the panel always closes onto a tab, and whether the next open shows the page again is decided by the flag alone: again while the notes are unseen, never once they are seen. The same function keeps the panel from reopening into Find, which also falls back when the panel is opened again without Find having been asked for.
- **While it shows.** It has no tab: `tab_emphasis` fades the lens so no icon is lit, and a change of tabs does not evict it. **Done** on the page asks the panel to leave (`leave_changes_when_done`), which switches to `way_back()`; a tab, the gear or the magnifier leave it like any page. While the notes are due, leaving it by one of those tells the app they are seen: `panel_ui` notes whether the page is being read before the header takes its presses (`reads_news`) and sends `Action::ChangesSeen` once if the header moved the pager off it (`walked_away_from_news`). Done sends its own and switches after that check, so it is never said twice, and a pager moved from outside the panel (`open_page`: a drop, a tool, a shortcut) says nothing. It is not one of the pages that hold the panel open, so the pointer leaving closes it after the usual grace, and that says nothing either.

Tests in `notch/tests/whats_new_page/mod.rs` open it by hover and by click over a filled shelf and a song, close and reopen it seen and unseen, and scroll a list of notes taller than the panel.

### Opening onto the walkthrough

A new install's first-launch walkthrough (`notch/panel/welcome.rs`, see [Platform: macOS](Platform-macOS.md#the-first-launch-walkthrough)) uses the same machinery one step earlier. `PanelData.welcome.due` is copied to `welcome_due` every frame, and `opens_to_start` asks `opens_to_welcome` before `opens_to_news`, so while it is due every open from rest, a peek or an activity lands on `Page::Welcome`. At launch the app opens it on the active display with `open_page`. Unlike What's New it holds the panel open (`Pages::holds_open`), because the pointer spends time in System Settings while you answer it; it still passes like What's New when the panel hides, and its **Done** leaves with `leave_welcome_when_done`.

### The page icons (`notch/panel/header`)

A row of icons, one per tab, sits along the top of the panel: on a hardware notch in the row just under the camera (the header is the notch height plus 44 points) with the gear in the right wing beside the camera, and on an island in a 48 point header with the gear at the right. Every tab gets the same 42 point slot (narrowing to 20 when there are more tabs than room), and the row stays centered on the panel while it fits, sliding left rather than running under the gear. Icons are 14 points and a dim white (40%); the current page's icon is full white and sits in a **glass lens**, a capsule of the same lit glass as the buttons (`panel/header/pill.rs`). Switching tabs springs the lens to the new tab, its leading edge running ahead so it stretches and thins like a drop; dragging along the row carries it under the pointer, lifting and swelling it and the icon under it, and letting go lands on the nearest tab. Hovering an icon brightens it. While Settings or Notifications shows, the lens fades and the gear gets its own round lens and turns white. While What's New shows, the lens fades as well and no icon is lit. The gear toggles Settings, going back to the tab you came from; Notifications opens from a row in Settings, so the gear also leads out of it. When a tab comes or goes while the panel is open, its place grows from nothing or folds away (`tab_rows`), so the other icons glide aside instead of jumping.

The gear carries a blue dot while a notification hasn't been seen, and the Agents tab a yellow one while any run waits on you, whichever tab is chosen. Both are the same dot (`panel/header/badge.rs`: `Badges` from `PanelData`, painted at the icon's top right); a tab's dot sits a point and a half further out than the gear's. Core tabs use fixed icons (a note for Media, a grid for Tools, a tray for Shelf, a speaker for Sound, a gauge for Stats, a sparkle for Agents) and a tool's tab uses the `page_icon` from its manifest, or a star.

### Black into glass (`notch/frame.rs`, `platform::Backdrop`)

Only the open panel fades into glass. Every other shape the notch takes is black all the way down: the resting notch, the peek and its strain, an activity, a notice, a question, the drop zone, the song, the volume strip, the wings beside a hardware notch and the ears. Over a bright wallpaper a small black shape that dissolves along its lower edge reads as a stain, not as glass, so the glass is kept for the one shape large enough to carry it. The shell is filled solid black and then, while the panel is open, `Notch::glass_fade` lays a **hole** over it (see [see-through glass](Rendering-and-Motion.md#glass)): a band of horizontal strips that takes nothing away down to 32% of the shape (never less than the header, or 40% of a shape shorter than that, so on a hardware notch the camera row stays black and the shape still merges with the housing) and then eases to taking 92% away at the bottom edge, leaving it 8% opaque. Its strength follows the panel's own fade (`Notch::open_glass`, the `panel_fade` spring), so the glass comes in with the page as the panel opens and is gone again before the shape has shrunk back. Because the hole is a plain rectangle of strips, the fade is level across the whole shape whatever its outline, and the shadow is painted after it so it still darkens the glass from behind. A floating island's [keyline](#the-keyline-notchkeyliners) comes last and fades with the glass. The shadow follows how open the panel is (`Notch::openness`: how far the shape has grown, or the panel's fade, whichever is more), so switching to a taller page, which moves the panel's target before the shape has grown, never drops the shadow out for a moment; tools reading `NotchState::expansion` see the same value. A scrolling page fades into the same color. Behind the window a macOS `NSVisualEffectView` (blending behind the window, `platform/macos/backdrop.rs`) blurs whatever is under the notch, with its tint taken out and its blur lightened so what is behind still shows through as soft shapes, masked each frame to the outline that was painted (`Notch::backdrop`, a `CAShapeLayer` path set without implicit animation; the plain silhouette, the straining one or the fleeing one, all from `Notch::body_outline`, and every ear's outline), so the blur is exactly where the shape is. **Buttons and wells are see-through in every state**, the closed ones included, and they are darker glass than the panel's fade: each is a **pane**, and the backdrop holds down what shows through it (see [smoked panes](Platform-macOS.md#the-blur-behind-the-panel-platformmacosbackdroprs)). A dark wallpaper shows through a button as it is, a bright one is held to a dark grey, so a button always keeps black in it instead of turning the color of the wallpaper. On a hardware notch the fade stays clear of the camera housing: `Notch::clear_of_housing` scales it to nothing within 6 points of the housing, beside it or below it, and back to full by 40 points, which matters while the panel is still short on its way open. On Windows there is no blur behind the window (`BLURS_BEHIND` is false) and the panel stays solid black.

### Pager (`notch/panel/pager.rs`)

The pager tracks the current page, the page it came from, a switch progress spring (`SMOOTH`) and the tab pill spring (`BOUNCY`). Switching slides the old page out and the new one in, in the direction of the tab you moved to, and retargets the panel height (`Motion::Resize`). Switching again before a switch has ended (`Pager::handover`) keeps whichever of the two pages shows more, at the strength it has, and drops the fainter one, so hopping across tabs never flashes a half-faded page back to full. Page heights are kept in a `HashMap<Page, f32>`; a page without a measurement yet counts as 84 points. When any height changes by more than a hundredth of a point, the panel morphs to fit, so the notch is always exactly as tall as its content, including the last fraction of a point a page's spring settles by. A page that grows or shrinks smoothly in place at rest (a tool's card, a dropdown, the mixer, a hovered Agents row) is followed closely (`Motion::Follow`, 0.1 s and critically damped), since its content already moves on its own spring and would otherwise run ahead of the panel's edge. A page that jumps to a new size at once (faster than 2,000 points a second, such as another Settings view) and a page switch keep the softer `Resize`.

### Page panel (`notch/panel/mod.rs`)

- **Measuring.** Every frame the panel asks each page for its natural height: the core pages directly, the Settings page for its current view, and each tool page through the element renderer's `Measure`.
- **Capping and scrolling.** A page may not be taller than the canvas allows: 600 points minus the header, padding and 34 points of room for the shadow. A taller page is shown at the capped height inside a clipped child `Ui`, and scrolls up and down with a mouse wheel (40 points per notch) or two fingers on a trackpad (1:1) while the pointer is over it; a mouse wheel's notch glides there on a quick spring (`Pages::glide_to`, 0.18 s) instead of jumping, while a trackpad follows the fingers exactly, unless a control under the pointer already took that scroll; a thin 3 point scrollbar in the right-hand padding shows the position. Each page remembers its own scroll offset; What's New alone starts at the top again once the panel has hidden.
- **Overflow cue** (`notch/panel/overflow.rs`). A clipped page fades into the panel's black at the edges, the way a list does under the bar in an Apple app, so a row cut off at the bottom reads as "more below" rather than a mistake. Each fade is a 24 point gradient (`Canvas::vertical_gradient`, eased with `smoothstep`) from the panel's black at the edge to clear inside, painted over the page's content and under the scrollbar. Its strength follows the scroll: the bottom fade is full while 24 points or more are hidden below and thins to nothing as the last row comes fully into view; the top fade grows the same way over the first 24 points scrolled. `Overflow` holds the window, natural height and offset of a scrolled page and gives the content rect, the clip (the window plus the scrollbar's gutter), both fade strengths and the scrollbar; a page that fits gets none of it. The panel's height, and so the pager's measuring, is unaffected. On the Mac, where the open panel turns to glass toward the bottom, each edge fades into what is really behind it (`Notch::backdrop_at`): the top edge into the black under the header, and where the backdrop is mostly clear glass the rows themselves dim as they near the edge instead of being painted over.
- **Swiping between tabs.** Two fingers sideways on a trackpad anywhere on the open panel moves to the neighboring tab, one tab per swipe however long it glides. Swipe left for the tab to the right. Controls that scroll sideways (sliders, the shelf row, a calendar) keep their own swipes, and a mouse wheel never switches tabs.
- **Layers.** During a switch two page layers are drawn: the outgoing page fades and slides away, the incoming page fades and slides in. Only the incoming layer, once it is more than half visible, gets full interactivity; the other is capped at 20% input alpha, so it cannot be clicked. Each page rises 6 points and grows from 92% as the panel opens. During a switch the incoming page is not held back until the panel has grown to its height: it fades in on the switch's own curve at full size, revealed by the panel's edge as the panel grows, so switching to a taller page (Tools to Settings) never leaves the panel empty for a moment. While a page is taller than the panel holds (growing or shrinking), it is clipped a padding's width (16 points) above the panel's bottom edge (`Notch::cramped`), so nothing it draws shows outside the rounded bottom corners.
- **Shortcut capture.** While a shortcut is being rebound, the panel runs `KeyCapture` on the keyboard input first, and a click outside the shortcut field cancels the rebinding. See [Pages](Pages.md#rebinding-shortcuts).
- **Closing.** When the panel is fully hidden, the Tools page and tool pages close their dropdowns and release text focus, Settings returns to its general view, and What's New frees its picture and gives the pager back to a tab (see [Opening onto What's New](#opening-onto-whats-new)). The panel counts as hidden on the first frames of an open too, until the shape has grown to the header.

#### Scrolling

*Code: `ui::scroll` (`crates/paint/src/scroll.rs`) and `src/ui/swipe.rs`.*

Every control reads the wheel through `scroll::read`, which turns trackpad points into notches (40 points each) and keeps the two axes apart. It counts a movement as smooth, the way a trackpad scrolls, when it comes in points (macOS) or in fractions of a notch: Windows reports every touchpad and high-resolution or free-spinning wheel as fractional wheel lines, while a clicky mouse wheel sends whole notches. With that, a trackpad works the way it does in macOS apps:

- **Up and down** (`scroll::down`) goes to things that scroll up and down: the page, dropdown and device lists, and picker wheels.
- **Sideways** (`scroll::across`) goes to things that move sideways: sliders, the media volume bar, per-app volume rows, the shelf row, the calendar. On a trackpad only a sideways swipe counts, so scrolling a page past a slider never changes it. A mouse wheel has only one direction, so it drives whichever of them is under the pointer.
- **One owner.** A control that uses a scroll claims it for that frame (`scroll::take`), and the page, then the tab swipe, only use what nobody claimed.
- **Whole steps.** Lists and picker wheels add small trackpad movements up (`scroll::Notches`) and move a row each time they reach a whole notch, instead of a row per event.
- **One page per notch.** On a clicky mouse wheel, things that turn pages move one page per notch, at most one every 0.15 seconds (`swipe::notch`), so spinning the wheel can't flood them.
- **One page per swipe.** On a trackpad, things that turn pages (the calendar, the tabs) move once per swipe (`swipe::once`, `swipe::either`): the swipe has to travel 1.2 notches, then the rest of it, including the glide after the fingers lift, is ignored. The next swipe counts as soon as the fingers touch the trackpad again, even while the last one is still gliding: `scroll::track` follows the phases macOS reports with each scroll event (fingers down, lifted, coasting) and numbers every new touch, and a swipe that sees a new number starts from nothing. Where the system reports no phases (Windows), a swipe is over once it has been quiet for 0.28 seconds. A calendar also takes an up-and-down trackpad swipe when its page can't scroll; the two directions add up separately and the one that travels farther turns the page, so a wobble sideways does not cancel a swipe up.

Pages receive a `PageCtx` with the egui `Ui`, a canvas, their content rect, their opacity, `dt` and the current time, draw themselves, and return actions. See [Pages](Pages.md).

## Previews and tests

`NOTCHBASE_PREVIEW` pins the notch in a given state with sample content (a song, a device, a question, and so on) for screenshots and visual checks; see [Previews](Previews.md).

The notch is tested without any window. `notch/tests/fixtures.rs` provides helpers such as an island notch, `settle` (steps springs until they rest), `draw_out` (brings the island out under a cursor position), fixed cursor positions over and away from the notch, sample songs, sample tool notices, tool views built from real SDK tools, key events, and a headless egui rig that runs full `ui` frames. Tests cover the hover state machine, zones, attraction continuity, hug, activities and tool notices (with their controls, in `notch/notice/tests`), the live activity, tabs and paging, the music strip and anticipation, and a test that paints every preview state in both styles.
